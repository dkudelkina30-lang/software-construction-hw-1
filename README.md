# ВышКат

Консольное приложение на C#: приём транспорта через техосмотр, постановка вещей на баланс, отчёт по количеству и энергии, список транспорта для новичков и инвентарная ведомость.


## Запуск

Все команды выполняются из корня проекта:

```bash
dotnet build
dotnet test

# ввод из scenario.txt (файл по умолчанию)
dotnet run --project src/VyshKat

# ввод из другого файла
dotnet run --project src/VyshKat -- demo.txt
dotnet run --project src/VyshKat -- мой_сценарий.txt
```

В комплекте два входных файла:

- `scenario.txt` - ручной сценарий: приём трёх единиц транспорта (одна отклоняется техосмотром), пример ошибочного ввода, две вещи, все три отчёта;
- `demo.txt` - запускает встроенный демонстрационный сценарий.

Меню:

```
1. Принять транспорт
2. Поставить вещь на баланс
3. Отчёт: количество и энергия
4. Транспорт для новичков
5. Инвентарная ведомость
6. Демонстрационный сценарий
0. Выход
```

### Ввод из файла

Программа читает команды только из текстового файла. Путь к файлу передаётся первым аргументом. Если аргумента нет, используется `scenario.txt` в текущей папке. Если файла нет, программа пишет «Файл не найден» и завершается.

Формат файла: одна строка - один ответ на очередной вопрос программы, в том порядке, в котором программа их задаёт. Например, приём самоката:

```
1                 ← пункт меню «Принять транспорт»
1                 ← вид: самокат
Ninebot Max G30   ← модель
8                 ← простота для новичка (1–10)
95                ← техническое состояние, %
0,6               ← расход энергии, кВт·ч/сутки (точка или запятая)
```

Последовательность вопросов по пунктам меню:

| Пункт | Строки после номера пункта |
|---|---|
| 1 - транспорт | вид (1 самокат, 2 велосипед, 3 электровелосипед), модель, простота, состояние; для самоката и электровелосипеда ещё расход |
| 2 - вещь | вид (1 шлем, 2 док-станция, 3 зарядный шкаф), наименование; для док-станции и шкафа ещё расход |
| 3, 4, 5, 6 | ничего - сразу выводится отчёт или демонстрация |
| 0 | выход |

Чтение реализовано в `App/ConsoleIO.cs`: класс получает `TextReader` (в программе это `StreamReader` файла) и печатает каждое прочитанное значение после вопроса, поэтому в выводе виден весь диалог. Если строка некорректна, выводится подсказка и читается следующая строка файла. Когда файл заканчивается, программа печатает «До свидания!» и завершается, даже если в файле нет `0`.

## Структура

```
src/VyshKat/
├── Program.cs              точка входа: открывает входной файл, собирает DI
├── Domain/                 модель
│   ├── IInventoryItem.cs   объект на балансе: имя, вид, инвентарный номер
│   ├── IEnergyConsumer.cs  потребитель энергии: суточный расход, кВт·ч
│   ├── Vehicle.cs          базовый класс транспорта: простота 1–10, состояние %
│   ├── Scooter.cs, ElectricBicycle.cs   электротранспорт (IEnergyConsumer)
│   ├── Bicycle.cs          велосипед, энергию не потребляет
│   ├── Thing.cs            базовый класс вещей
│   └── Helmet.cs, DockStation.cs, ChargingCabinet.cs
├── Services/
│   ├── IServiceCenter.cs   интерфейс техосмотра
│   ├── ServiceCenter.cs    правила техосмотра
│   ├── InspectionResult.cs решение: принят / нет + причина
│   └── FleetService.cs     учёт парка и отчёты
└── App/
    ├── ServiceRegistration.cs  регистрация в DI-контейнере
    ├── ConsoleIO.cs            чтение из файла с проверкой
    └── ConsoleApp.cs           меню и демо
tests/VyshKat.Tests/        тесты
scenario.txt, demo.txt      входные файлы
```

## Модель и правила

- Транспорт (`Vehicle`) и вещи (`Thing`) реализуют `IInventoryItem` - у них есть инвентарный номер. Сотрудники в будущем этот интерфейс реализовывать не будут, поэтому на баланс не попадут.
- Расход энергии есть только у тех, кто реализует `IEnergyConsumer`: самокат, электровелосипед, док-станция, зарядный шкаф. У велосипеда и шлема этого свойства нет совсем.
- Номера общие для транспорта и вещей (`VK-0001`, `VK-0002`, …). Их выдаёт `FleetService` при постановке на баланс.
- Техосмотр (`ServiceCenter`): транспорт принимается, если состояние не ниже 60% и (для электротранспорта) расход не больше 3 кВт·ч в сутки. Отклонённый транспорт в парк не попадает и номер не получает. Вещи ставятся на баланс без техосмотра.
- Для новичков: простота ≥ 6.

## Функциональные требования

| № | Требование | Где |
|---|---|---|
| 1 | Добавление транспорта | `FleetService.AcceptVehicle`, пункт меню 1 |
| 2 | Техосмотр перед приёмкой | `IServiceCenter` / `ServiceCenter` |
| 3 | Суммарное потребление энергии | `FleetService.GetTotalDailyEnergy`, пункт 3 |
| 4 | Список для новичков | `FleetService.GetBeginnerVehicles`, пункт 4 |
| 5 | Вещи и инвентарные номера вместе с техникой | `RegisterThing`, `GetAllItems`, пункты 2 и 5 |
| 6 | Демонстрация сценариев | пункт меню 6 (файл `demo.txt`): три приёма, два отказа по разным причинам, три вещи, все отчёты |

## SOLID

- **S.** Классы разделены по задачам: правила техосмотра - в `ServiceCenter`, учёт и отчёты - в `FleetService`, чтение ввода - в `ConsoleIO`, меню - в `ConsoleApp`.
- **O.** Новый вид транспорта - новый наследник `Vehicle`, а `FleetService`, отчёты и техосмотр не меняются. Другие правила техосмотра - новая реализация `IServiceCenter`.
- **L.** Любой наследник `Vehicle` работает в `FleetService` одинаково. Расход энергии вынесен в отдельный интерфейс, чтобы велосипеду не пришлось возвращать фиктивный 0.
- **I.** Интерфейсы маленькие: `IInventoryItem`, `IEnergyConsumer`, `IServiceCenter`. Шлем не обязан иметь расход энергии.
- **D.** `FleetService` зависит от абстракции `IServiceCenter` и получает её через конструктор из DI-контейнера (`ServiceRegistration`).

## Ответы на обязательные вопросы

**Какой принцип применён наиболее явно и где?**
Dependency Inversion. `FleetService` (`Services/FleetService.cs`) не создаёт техосмотр сам и не знает его правил: он получает `IServiceCenter` через конструктор, а реализацию выбирает DI-контейнер в `App/ServiceRegistration.cs`. Поэтому в тестах техосмотр подменяется на fake без изменений в `FleetService`.

**Какой принцип сознательно ограничен и почему это приемлемо?**
- *OCP в консоли.* Вид транспорта и вещи выбираются через `switch` в `ConsoleApp.AddVehicle` / `AddThing`. При новом виде сюда добавляется одна ветка. Это единственное место, которое правится в интерфейсе; модель, сервис и отчёты не меняются.
- *SRP в `FleetService`.* Он и хранит списки, и выдаёт номера, и считает отчёты.

**Что сломается при расширении?**
- *Новый вид транспорта* (моноколесо): класс `Monowheel : Vehicle, IEnergyConsumer` + ветка в `switch` в `ConsoleApp`. Техосмотр, энергия, список для новичков и ведомость заработают сразу.
- *Сотрудники*: новый класс, который не реализует `IInventoryItem`. Учёт парка не меняется, в ведомость сотрудники не попадают.

**Какой тест фиксирует решение техосмотра и правило для новичков; как подменяется зависимость?**
- Правила техосмотра: `ServiceCenterTests` (граница 60%, износ, большой расход).
- Правило для новичков: `FleetServiceTests.BeginnerRuleIsSimplicityAtLeastSix` (простота 5, 6, 10).
- Подмена техосмотра: `FleetServiceTests` используют `FakeServiceCenter` - он всегда принимает или всегда отклоняет и считает вызовы. Подмена идёт через DI-контейнер: после штатной регистрации `IServiceCenter` регистрируется ещё раз на fake, и контейнер отдаёт последнюю регистрацию:

  ```csharp
  new ServiceCollection()
      .AddVyshKat(io)
      .AddSingleton<IServiceCenter>(fake)
      .BuildServiceProvider();
  ```

  `RejectedVehicleIsNotAdded` проверяет, что при отказе машина не попала в парк и не получила номер. `FleetTrustsServiceCenterDecision` проверяет, что изношенный самокат принимается, если так решил fake.

## Использование ИИ
ИИ использовался в качестве вспомогательного инструмента: для получения ответов на вопросы по языку программирования C#, разъяснения отдельных конструкций и моментов. Весь код написан и протестирован автором самостоятельно. ИИ выступал лишь в роли помощника.


## Тесты

- `ServiceCenterTests` - правила техосмотра.
- `FleetServiceTests` - приём и отказ с fake-техосмотром, вещи без техосмотра, энергия, новички, общие номера.
- `ConsoleAppTests` - сценарии меню: входные строки подаются так же, как из файла (через `StringReader`), проверяется вывод, в том числе ошибочные строки и конец файла.
